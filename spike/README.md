# Spike — throwaway

Single-page proof that mic → AudioWorklet → YIN → note name works before anything real is
built. **This code is disposable.** No framework, no build step, no dependencies.

## Purpose

1. De-risk `AudioWorklet` (TECH_DECISIONS ADR-002) — the single largest unknown in week 1
2. Fill every `[TBM]` field in `docs/AUDIO_PIPELINE.md`
3. Answer open questions 2 and 3 in `docs/MANIFEST.md`

## Run it

```sh
cd spike
python3 -m http.server 8000
# open http://localhost:8000/
```

A server is required: `getUserMedia` refuses to run from `file://`. Use Chrome — Safari
is not a success criterion (§8).

```sh
node --expose-gc verify.mjs    # 25 correctness checks on Stages A–F
node measure.mjs               # synthetic measurements → RESULTS.md
```

## Files

| File | What it is |
|---|---|
| `index.html` | The spike page: live tuner, pitch trace, and the §7.1 measurement panel |
| `dsp-core.js` | Stages A–G. Loaded verbatim by the worklet, the offline replay and Node |
| `verify.mjs` | Correctness checks — run this after touching `dsp-core.js` |
| `measure.mjs` | Synthetic measurements that need no hardware |
| `RESULTS.md` | Generated by `measure.mjs`. Not a substitute for the hardware runs |

**Why not one file.** §9 asks for a single HTML file. `dsp-core.js` is split out because
the octave-error comparison in §7.1 says "same input both times" — which also has to mean
*same code* both times. One copy of the DSP is shared by the worklet, the offline replay
and the Node harness, so the A/B cannot drift. Still no build step and no dependencies.

**Why not Pitchy.** §3 Stage C prefers a maintained library. An `AudioWorkletGlobalScope`
cannot `import`, so using Pitchy means a bundler, which §9 rules out. YIN is implemented
directly in `dsp-core.js` (~90 lines, de Cheveigné & Kawahara steps 1–5) and checked
against synthesized tones in `verify.mjs`. **The engine should still use Pitchy** — this
is a spike-only shortcut, not a recommendation.

## What the page does

- **Live readout** — note name, cents, Hz, clarity, RMS, frames/sec, running latency
- **Trace** — raw Stage E output dim violet, Stage F output bright; toggle the filter to
  see the difference. Y axis linear in semitones. Onset-suppressed frames render dim red
  so you can count how many attack frames are garbage
- **Calibrate** — record silence, then a quiet note; suggests a `gateThreshold` and
  writes it into the profile table
- **Measurements** — pipeline latency, acoustic loopback, accuracy sweep, octave A/B on a
  recorded take, metronome bleed. Everything lands in a markdown log you can copy out

**ADR-002 is de-risked.** The AudioWorklet path runs in Chrome: worklet module
compiles from a blob, the processor runs on the audio thread, frames reach the main

## Findings so far

**OQ3 is answered.** The floor is `sampleRate / (windowSize/2 - 1)` = **46.9 Hz** at
2048/48 kHz, matching the "~45 Hz" in §3 Stage A. Cello low C (65.4 Hz) is fine. Bass low
E (41.2 Hz) and piano A0 (27.5 Hz) produce **no detection at all** — the safe failure, not
a wrong pitch. 4096 samples resolves both at 85 ms window latency and 2× CPU.

**New: sub-octave errors above ~2.5 kHz.** Not anticipated anywhere in the document.
Where the true lag falls near a half-integer (14.45 samples at 3322 Hz), no integer lag
correlates well but 2× does, so YIN locks the sub-octave — on *every* frame, with clarity
0.98. All three §5 defenses miss it: the sub-octave is inside the range clamp, and the
median filter agrees with itself. Measured 32% of test frequencies in 3000–3600 Hz. This
affects **violin (fMax 3600)** and **piano (fMax 4200)**; flute and clarinet cap at 2200
and are clear. An optional submultiple guard removes it entirely and leaves C2–C6
untouched, at the cost of dropping 26.5% of high frames below the clarity gate. It is
**off by default** — the spec'd algorithm is what runs unless you turn it on. See
RESULTS §6.

**CPU scales with `1/fMin`,** so the §6 range clamp is a CPU control as well as an
accuracy one: soprano costs 2.2% of one core per frame, piano 11.1%.
